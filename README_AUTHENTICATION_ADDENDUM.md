## 运行架构与认证边界

本项目当前是由用户提供给 AI 平台读取的 Markdown 规则文件，不是独立运行的 Web 应用、API 服务或 SaaS 产品。因此，V1.0 不实现用户注册、登录、会话管理或应用级 Token 认证。

需要区分三个不同的责任层：

1. **GitHub 仓库访问控制：** GitHub 负责仓库查看、Fork、Issue、Pull Request 和写入权限。仓库权限不等于本 Skill 的用户身份认证。
2. **AI 平台身份与模型访问：** 用户登录、订阅、模型调用授权以及平台内部凭证，由实际使用的 AI 平台负责。本 Skill 不接管这些流程。
3. **Skill 规则执行：** `SKILL.md` 定义 AI 如何理解输入、选择模式和组织输出，不负责验证用户身份，也不能替代平台安全控制。

### 凭证与敏感信息原则

- 不要把 GitHub Personal Access Token、API Key、密码、Cookie、Session ID 或其他秘密凭证写入 `SKILL.md`、README、Issue、示例、提交记录或公开仓库。
- 不要要求用户把 AI 平台密码或登录 Token 粘贴给 Skill。
- 如果未来增加 API 集成，应由独立的应用或服务端安全管理凭证；优先使用最小权限、环境变量或专用密钥管理服务，避免将秘密暴露给浏览器端和模型提示词。
- 如凭证意外进入 Git 历史，应立即在对应平台撤销或轮换凭证；仅从当前文件删除并不能保证历史副本消失。
- 不要把模式前缀、对话中的自我声明或 AI 对规则的遵循视为身份验证或授权证明。

### 未来何时才需要认证

只有当项目演进为独立在线产品，并确实需要用户账号、云端保存个人提示词、跨设备同步、团队协作、付费订阅或受保护的 API 时，才应单独设计认证架构。

届时应按实际需求评估托管身份认证、服务端会话、权限模型、数据隔离和密钥管理，而不是直接把 JWT 或 Token 机制塞进当前 Markdown Skill。

详细安全原则见 [SECURITY.md](SECURITY.md)。
